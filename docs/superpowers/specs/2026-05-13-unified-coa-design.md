# Unified Chart of Accounts — Design Spec

**Date:** 2026-05-13
**Status:** Approved (pending written-spec review)
**Author:** brainstorming session

## Problem

The current system carries two parallel-but-overlapping tables for "what bucket does a money movement go into":

- **`chart_of_accounts`** — the real accounting GL (26 entries: 1xxx assets, 2xxx liabilities, 3xxx equity, 4xxx revenue, 5xxx expense). Has a 5-value `account_type` enum (`asset | liability | equity | revenue | expense`). Engineering / migration-managed.
- **`payment_categories`** — a user-facing label layer (11 entries) Finance maintains in Settings. Each row carries a `label` (display name), an `account_type` (Balance Sheet vs P&L classification), and a `gl_account_code` pointing back at `chart_of_accounts`.

The two tables are kept in sync by an `account_type-matches-GL-type` trigger. That sync is fragile: users have already mis-classified rows (e.g. `amount_due_to_lim_wei_liang` labelled "Amount Due TO" but classified `asset` pointing at `1000 Assets`). The two layers also produce a coarseness mismatch: most user categories map to a tiny set of GL accounts (`5050 G&A`, `1000 Assets`), so the GL gives no useful breakdown and the categories give no enforced accounting discipline.

The Income Statement and Balance Sheet structure that fall out of the current 5-type enum are coarser than a working business needs:

- No separation of **Fixed Asset** vs **Current Asset** (everything's `asset`).
- No separation of **Cost (COGS)** vs **Expense (OpEx)** — no Gross Profit line.
- No **Other Income** bucket — interest income, penalty income lump with main revenue.
- No structured **Cash Flow Statement** — the current per-pool view doesn't distinguish Operating / Investing / Financing activities.

## Goal

Replace the two tables with a single **Chart of Accounts** (one source of truth), expanded to eight account types with controlled numeric ranges and auto-generated codes. Drive every report (P&L, BS, CFS) from this single COA, including a proper standard structure (Gross Profit, Other Income, Op/Inv/Fin activities).

User experience:
- Finance picks one of eight types when creating an account; names it; system generates a code from the type's range. Code is locked after creation.
- Reports are organised by type at the summary level and by account name at the detail level.
- Cash Flow shows Operating / Investing / Financing sections; each section can drill down into pool subgroups.

## Approach

**Big-bang migration.** The system is in a test state with minimal business data (1 fund source, 1 loan, 5 payment vouchers, 1 invoice, ~36 journal lines). The cleanest path is: run the existing `wipe-all-business-data.mjs` again to clear transactional data, then apply schema changes and reseed `chart_of_accounts` under the new scheme, then the user re-enters business data using the new account picker.

Considered and rejected:
- **Phased migration** (run old + new in parallel during a transition window) — overhead far exceeds risk reduction given near-empty data.
- **Schema refactor without renumbering** (merge tables but keep current 1xxx/2xxx/3xxx scheme) — doesn't deliver the user's chosen ranges, only solves half the problem.

## Design

### 1. Data model

#### 1.1 `chart_of_accounts` (single table, replaces the pair)

Columns (changes from current schema in **bold**):

| Column | Type | Notes |
|---|---|---|
| `code` | `VARCHAR(10)` PRIMARY KEY | Auto-generated by `next_account_code(type)` RPC, locked after insert |
| `name` | `TEXT NOT NULL` | User-provided, e.g. "Office Rental" |
| `type` | **`account_type` NOT NULL** | Enum expanded to 8 values (see §1.2). NOT NULL was added by mig 234 |
| **`cash_flow_category`** | **`cash_flow_category NOT NULL`** | New enum: `operating | investing | financing`. Default derived from `type` at insert (see §1.3) but user can override |
| `is_active` | `BOOLEAN NOT NULL DEFAULT TRUE` | Soft delete; cannot hard-delete |
| `sort_order` | `INTEGER NOT NULL DEFAULT 100` | Display ordering within a type |
| `created_by` | `UUID REFERENCES users(id)` | Audit |
| `created_at` | `TIMESTAMPTZ NOT NULL DEFAULT NOW()` | Audit |

Constraints:
- `CHECK (code::INT BETWEEN range_start AND range_end)` enforced by a trigger using §1.2's ranges (DB-level guard against out-of-range manual SQL).
- `name` is `UNIQUE per type` (case-insensitive) — avoids two "Office Rental" rows under Expense.

#### 1.2 Eight-type enum and number ranges

`account_type` is replaced by:

| New enum value | Range | Range notes |
|---|---|---|
| `equity` | 1000-1999 | Permanent equity, pools |
| `fixed_asset` | 2000-2999 | Property, equipment (future depreciation hooks) |
| `asset` | 3000-3999 | Current assets — cash, AR, loans receivable, advances |
| `liability` | 4000-4999 | Payables — fund sources, salary, statutory |
| `revenue` | 5000-5999 | Main-business income |
| `cost` | 6000-6999 | COGS — direct cost of revenue |
| `other_income` | 7000-7999 | Non-main income — interest, penalty |
| (gap) | 8000-8999 | Reserved for future use |
| `expense` | 9000-9999 | Operating expenses (G&A, salary, marketing, interest) |

Reserved 8000-8999 gap is intentional and documented in the seed comment so a future "Other Expense" or similar can slot in.

The Postgres enum migration appends the new values (`fixed_asset`, `cost`, `other_income`) alongside existing ones. Existing rows mapped before the wipe runs (but they're being wiped anyway, so the mapping is only relevant for the seed run).

#### 1.3 `cash_flow_category` default mapping

A new Postgres enum `cash_flow_category` with values `operating | investing | financing`. Each `chart_of_accounts` row carries one, defaulting at insert time by the account's `type`:

| Account `type` | Default `cash_flow_category` | Rationale |
|---|---|---|
| `equity` | `financing` | Capital movements |
| `fixed_asset` | `investing` | Asset acquisition / disposal |
| `asset` | `operating` | AR collection, advances — operating in most cases |
| `liability` | `financing` | Borrowing / repayment |
| `revenue` | `operating` | Main business |
| `cost` | `operating` | COGS |
| `other_income` | `operating` | HV's loan-interest income is a treasury-business item; main-business adjacent |
| `expense` | `operating` | OpEx |

User-overridable per-account. The seed COA assigns explicit values where the default doesn't fit:

- `3020 Loans Receivable` → **`investing`** (HV lending is an investing activity, not operating AR collection)
- `7000 Interest Income — Loans` → keep `operating` (HV treats lending as part of main business)
- `4010 Interest Payable — Fund Sources` and `9010 Interest Expense — Fund Sources` → keep `operating` (consistent with treasury treatment)

UI: a single dropdown next to the Type field, prefilled with the default, editable.

#### 1.4 Drop `payment_categories`

The entire `payment_categories` table is dropped. Triggers and FKs referencing it are removed in the same migration.

#### 1.5 `payment_voucher_sources` field rename + FK retarget

- Column `category_code` is renamed to `account_code`.
- The FK (added by mig 235: `pvs_category_code_fk → payment_categories(code)`) is dropped and replaced by `pvs_account_code_fk → chart_of_accounts(code)`.
- All code references (`src/lib/cfo-reports.ts`, `src/app/(portal)/payments/actions.ts`, `src/lib/voucher-paid-helpers.ts`, etc.) are updated to read `account_code` and join to `chart_of_accounts`.

### 2. Auto-code generation RPC

```sql
CREATE FUNCTION next_account_code(p_type account_type)
RETURNS VARCHAR(10) LANGUAGE plpgsql AS $$
DECLARE
  v_start INT; v_end INT; v_max INT;
BEGIN
  CASE p_type
    WHEN 'equity'        THEN v_start := 1000; v_end := 1999;
    WHEN 'fixed_asset'   THEN v_start := 2000; v_end := 2999;
    WHEN 'asset'         THEN v_start := 3000; v_end := 3999;
    WHEN 'liability'     THEN v_start := 4000; v_end := 4999;
    WHEN 'revenue'       THEN v_start := 5000; v_end := 5999;
    WHEN 'cost'          THEN v_start := 6000; v_end := 6999;
    WHEN 'other_income'  THEN v_start := 7000; v_end := 7999;
    WHEN 'expense'       THEN v_start := 9000; v_end := 9999;
  END CASE;

  SELECT COALESCE(MAX(code::INT), v_start - 1) INTO v_max
  FROM chart_of_accounts
  WHERE code::INT BETWEEN v_start AND v_end;

  IF v_max + 1 > v_end THEN
    RAISE EXCEPTION '% range exhausted (>% codes used)', p_type, v_end - v_start;
  END IF;
  RETURN (v_max + 1)::TEXT;
END $$;
```

The Server Action that creates an account calls this RPC inside a transaction, then `INSERT`s the row with the returned code.

### 4. UI changes

#### 4.1 Settings → "Accounts" tab (renamed from "Categories")

Create form:
- **Type** select (8 options, each labelled with its range — e.g. "Expense (9000-9999)")
- **Cash flow** select (`Operating / Investing / Financing`), prefilled by type default
- **Name** text input, required
- **Code** read-only label — shows "(auto-generated on save)" before submit, the actual code after submit
- Submit button

List view:
- Grouped by type, sorted by code within each group
- Each row: code · name · cash flow category · status · Edit link
- Filter for active/inactive

Edit modal:
- Editable: `name`, `cash_flow_category`, `is_active`, `sort_order`
- Read-only (greyed out): `code`, `type`

Soft delete on `is_active = false`. If any `journal_lines.account_code` references the account, edit and deactivate are still allowed (history stays valid), but a future "merge accounts" tool is out of scope.

#### 4.2 `/payments/new` (PV creation form)

The current "Category" dropdown becomes an "Account" dropdown sourced from `chart_of_accounts`, grouped by type, only showing `is_active = true`. Default-filter to expense-type accounts for debit vouchers and revenue-or-asset accounts for credit vouchers — soft hint, user can pick any.

### 6. Migration sequence

Single migration file produces the schema and reseeds:

1. `ALTER TYPE account_type ADD VALUE 'fixed_asset'`, `'cost'`, `'other_income'` (Postgres enum extension; each in its own statement per Postgres requirements).
2. `CREATE TYPE cash_flow_category AS ENUM ('operating', 'investing', 'financing')`.
3. `ALTER TABLE chart_of_accounts ADD COLUMN cash_flow_category cash_flow_category` (NOT NULL deferred until reseed).
4. `DROP TABLE payment_categories CASCADE` (drops the FK from `payment_voucher_sources.category_code` automatically).
5. `ALTER TABLE payment_voucher_sources RENAME COLUMN category_code TO account_code`.
6. Add FK `payment_voucher_sources.account_code → chart_of_accounts(code)`.
7. Add the range-enforcement trigger on `chart_of_accounts.code`.
8. `CREATE FUNCTION next_account_code(account_type)` as in §2.
9. `DELETE FROM chart_of_accounts` (wipe the old seed).
10. `INSERT` the 28 seed rows from §3, including `cash_flow_category` values.
11. `UPDATE bank_accounts SET gl_account_code = '3000' WHERE bank_name = 'Hong Leong Bank'`, etc.
12. `ALTER TABLE chart_of_accounts ALTER COLUMN cash_flow_category SET NOT NULL`.

Before the migration is applied, the user runs `scripts/wipe-all-business-data.mjs --confirm` again to clear the few test transactions, then applies migrations 234, 235, 236 (the previous batch — assuming they haven't been applied yet), then this new migration. The order is: wipe → 234/235/236 → new COA migration. (If the previous batch has been applied, this migration runs alone after the wipe.)

The CategoriesSection UI component is renamed to AccountsSection. The Server Action `createPaymentCategory` becomes `createAccount`. The `account_type` field becomes `type`. UI option labels include the type's range.

### 7. Testing

- **Pure-function tests** in `src/lib/coa.ts` (new): `defaultCashFlowCategoryFor(type)` returns the right default; range constants are exported and used consistently.
- **DB function test** (Postgres): `next_account_code('expense')` returns `9000` when the range is empty, `9001` after inserting one expense, throws when the range is full.
- **classifyRows** (existing test file) extended: a row with `cash_flow_category = 'investing'` lands in the cash flow's `investing` section, not `operating`.
- **Income Statement** test: with Revenue 10k + Cost 3k + Other Income 200 + Expense 1.5k, Gross Profit = 7k and Net Profit = 5.7k.
- **Migration smoke test**: after applying, verify all 28 seed rows exist with the right type/range/cash_flow_category and that the bank_accounts FK points at the new codes.

## Out of scope

- Hierarchical sub-groups (Asset > Current > Bank). Two levels (type → account) only.
- Account-merging tool (combining two accounts into one for de-duping).
- Depreciation logic for Fixed Assets (deferred until there are actual fixed-asset transactions).
- Multi-currency.
- Year-end closing entries that roll Revenue/Expense into Retained Earnings.
- An "Other Expense" category in the 8000-8999 gap (reserved but unused).

## Open items for the implementation plan

- Whether to keep `bank_accounts` as a separate table or fold it into chart_of_accounts (1010 / 1011 already exist as 3000 / 3010 in the new scheme — `bank_accounts` carries extra fields like account number, swift code; keep it but ensure FK from `bank_accounts.gl_account_code` to `chart_of_accounts.code`).
- Whether `salary_pool` and `dept_pools` tables continue as sub-ledgers or merge into the GL via the equity 10xx accounts (this is a separate audit item — Audit #5 from the prior session; flagged as a follow-up).
- Whether `cash_flow_category` should also be settable per-PV (override the account's default for a specific transaction) — defer; account-level default is enough for now.
