# Every tab — the installed app (PWA)

Installing the portal, a release reaching apps left open, the phone's own navigation bar. Read this before changing any of them, and again in every full scan of such a change (CLAUDE.md › Rules by tab). CLAUDE.md › Coding Conventions keeps the summary. Until 2026-10-10 these were the INSTALLABLE paragraph of the `(member)/member/` tree comment and two paragraphs of Coding Conventions, moved word for word.

**INSTALLABLE (2026-09-23):** the whole portal is a PWA — ONE app, `start_url` `/` (which already routes member → /member, everybody else → /dashboard). `public/manifest.webmanifest` is linked BY HAND in the root layout's <head>: an `app/manifest.ts` gets streamed into <body> and Chrome then refuses to install. `public/sw.js` caches NOTHING but `offline.html` — every page is somebody's money, and a cached copy would outlive the session on a shared phone. Install entry points: login card, member Profile row, Principal Profile card (`components/pwa/`, `lib/pwa/install.ts`). Icons from `tools/generate-pwa-icons.mjs`.

A release reaches open apps (2026-10-06) — an installed app is resumed from memory, not reloaded, and the member app changes screens with `history.pushState` and reads through Server Actions, so it never makes the navigation that would meet a new build; and Next recalculates every Server Action's id per build, so a copy left open across a release starts failing its reads. The service worker is NOT the cause (it caches no page). The build names itself: `next.config.ts` bakes `VERCEL_DEPLOYMENT_ID || VERCEL_GIT_COMMIT_SHA` into the bundle as `NEXT_PUBLIC_APP_VERSION` and answers it on `/sw.js` as `X-App-Version` (empty off Vercel = never prompts). `components/pwa/UpdatePrompt` (root layout) asks with a plain HEAD — no deployment pin, so Skew Protection cannot keep it on the old build — on load, on every return to the screen (`visibilitychange`, `pageshow`), on `online` and every 5 min in view; a newer build is OFFERED (*A new version is ready* · Update · ×), and IN THE REVENUE APP ONLY (`/member`, `mayReloadOn`) after 30+ min away it reloads on return unless a field still had the focus or something was typed in the 10 min before leaving (`lib/app-update.ts`, user chose A 2026-10-06). The portal is only ever offered it: HR › Payroll holds edits until *Save all* without a `beforeunload` guard, and edits made long before a tab switch are invisible to any typing check — a reload there could cost unsaved pay. The member app's quote survives a reload (tab `sessionStorage`). Nothing reloads by itself while on screen. DESIGN.md › Update prompt.

The phone's navigation bar after a reload (2026-10-10) — the installed app draws under the phone's own buttons (`viewport-fit=cover`) and its bottom bars stood on `env(safe-area-inset-bottom)`; after a reload (Update, a stale-action pull, Try again) on an Android phone with three-button navigation the Revenue app's bar sat BEHIND those buttons, only its top edge and the Quote circle showing (user's screenshot) — by its geometry the page still drawn under them and the inset back at 0 (reproduced with CDP `Emulation.setSafeAreaInsetsOverride`: 48 → reload at 0 gives the same picture). Chrome's edge-to-edge controller does not re-push an unchanged bottom inset for a new document and returns early for a tappable three-button bar (read in Chromium's `EdgeToEdgeControllerImpl`, not seen on the device). So every bottom bar, and what pads itself clear of one, uses `var(--safe-bottom)` = max(the browser's inset, `--safe-bottom-floor`): `components/pwa/SafeAreaMemory` (root layout) reads the real inset off a probe, remembers a non-zero one with its window in `sessionStorage` (`vp-safe-bottom`), and a page that has heard only 0 in exactly that window stands on it — set before the first paint by the head script `SAFE_BOTTOM_BOOT`, lifted the moment the browser speaks (`lib/safe-area.ts`). A fresh launch, a desktop and a phone with no bar are untouched. `src/lib/safe-area.test.ts` refuses a new bare `env(safe-area-inset-bottom)` outside the previews. The Revenue app's SHEETS reach the screen's bottom edge too (`Sheet.tsx` `.panel`, `.psPanel` + its bed-frame `.pickPanel`, Notifications `.page`, View as `.va`): each carries a transparent `border-bottom: var(--sheet-safe)` (shell.module.css `.screen`) = only what its drawn 24–34px bottom padding does not cover — iPhone `--safe-bottom − 30px` (34 → 4px, looks as drawn), Android `− 6px` (three buttons 48 → 42px, clear by 12–28px) — taken out of the sheet's height so it covers no more of the screen. DESIGN.md › The phone's own navigation bar.

**THE HR APP INSTALLS AS ITS OWN (2026-10-11, the HR revamp's second package — the user: "HR app at /hr-app, installable"):** `/hr-app` has its own manifest, `public/hr-app.webmanifest` (`id` / `start_url` / `scope` `/hr-app`, *HOUZS HR*, short name *HR*, the portal's icons). The root layout's hand-written `<link rel="manifest">` stays the portal's; the HR app swaps its `href` on mount and puts it back on the way out (`components/hr-app/HrAppManifest.tsx`) — Chrome re-reads a manifest whose link changes, and iOS reads the link when *Add to Home Screen* is pressed. Signed out, the app sends you to `/login?next=/hr-app`, the only return the sign-in honours. `sw.js` is unchanged (still `offline.html` only). The rules: `../hr/hr-app.md`.
