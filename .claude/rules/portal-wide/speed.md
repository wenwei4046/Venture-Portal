# Every tab — navigation speed

Read this before adding or changing a page, a route, a read or a list — in any tab — and again in every full scan of such a change (CLAUDE.md › Rules by tab). CLAUDE.md › Coding Conventions keeps its summary. Until 2026-10-10 this was that paragraph in full, moved word for word.

Navigation speed (2026-09-26) — a click must answer at once. Every route folder with child routes has a `loading.tsx` rendering `RouteSkeleton` (`src/app/route-boundaries.test.ts` fails otherwise): without it Next keeps the page being left frozen until the server answers. The client router keeps pages FIVE MINUTES (`experimental.staleTimes`, 30 s until 2026-10-08), so a write must `revalidatePath` (or set a cookie) before it redirects — that is what empties that memory — and a page shown from memory refreshes itself behind the click (`components/layout/RouteFreshener.tsx`, `lib/route-freshen.ts`: no skeleton and no `?_rsc=` fetch of that path since the click = from memory → `router.refresh()`; never an `AUDITED_ROUTES` page). A component holding unsaved edits must survive a refresh — keep a field's typed value over new props the way `PayrollRow` / `AmountInput` / `DirectorPoolClient` do (user 2026-10-08: 切换到另外一个 tab 都非常的慢 … 我要它做到真正的快). Warm a page only through `lib/nav-warm.ts` (`warmOnIntent` / `warmRoute` / `warmWhenIdle`): one link at a time, never an `AUDITED_ROUTES` page — a full prefetch reaches the server as a render, so a page that writes access_log while rendering would log a view for a mouse-over. The Sidebar also warms the person's usual pages (`recordVisit` / `usualPages`, opened ≥2 times, three at most, 2 s after the last navigation, 700 ms apart, desktop only). Nothing may fire a Server Action on its own after a navigation (page views go through `lib/page-view.ts` from the browser): Next refreshes the whole page after any navigation that interrupts a pending action. Progress: `NavProgress` in the root layout, started by `src/instrumentation-client.ts`; DESIGN.md › Navigation feedback (v3.8). A page's independent reads start together and only real dependencies wait (the month page `revenue/[sub]/[period]/page.tsx` is the pattern; wrap a PostgREST builder you await twice in `Promise.resolve` — awaiting a builder again sends it again). `fetchByKeys` runs 4 chunks at a time. A read started ahead of its `await` goes through `startRead` (`lib/start-read.ts`: one request, marked handled — a page that returns or throws first leaves no unhandled rejection), and answers are awaited in the old order so the same failure surfaces first. A whole table goes through `fetchAllRowsParallel` (the first page asks the count, the rest go 4 at a time; every GL report 2026-10-08: 5–12 round trips in a row → 2–3), an id list of unknown length through `fetchByKeys`, never one `.in()` (418 voucher ids = a 16 KB URL). A read — or an rpc returning rows — that can pass 1,000 rows is PAGED: PostgREST stops at 1,000 without a word (2026-10-08: Journal Entries showed "0 lines" on vouchers past the 1,000th journal line; the sales file import lost the brand of 553 of 1,553 products). Where the page leans on the read's tie order (labels joined as they arrive, a stable sort's ties), `fetchAllRowsAsWritten`: sent as written while under the cap, paged with an `id` tiebreaker only when full. The department registry (`lib/dept-registry.ts`) is module state `createClient()` refreshes every 30 s, beside the request (only an instance's first read waits), from a SIGNED-IN request only, and an empty read never replaces it: RLS shows departments to a session alone, and a sign-in landing on a due refresh used to empty it for every request on the instance (2026-10-08: Dept Pool's bank balance RM 254k for 507k). Two database traps behind the 3–10 s month page (mig `20260926100000`): a SQL function that calls another SQL function PER ROW re-checks the caller's permissions on every call (`has_scope`, ~1.7 ms each — 317 bills = 1.5 s), so join the answer once instead; and under RLS only LEAKPROOF comparisons reach an index (int, date and text equality do; numeric and enum comparisons do not), so a big lookup table searched by an amount needs a SECURITY DEFINER function (`lookup_pcb`). **The permission helpers are plpgsql (2026-10-09, mig `20261009070000`):** Postgres 17 never inlines a SECURITY DEFINER function and plans a `LANGUAGE sql` body again on EVERY call, and a row policy calls its helper once per statement — so every query paid for planning `has_scope` (1.7 ms), `has_action` / `has_any_action` (~6 ms), `may_write` (10–18 ms). As plpgsql (same body, `BEGIN RETURN (…); END`) the plan is kept for the connection: 0.23 / 0.73 / 0.78 / 0.80 ms. Thirteen helpers, answers checked identical on production for every login and template; `src/lib/permission-helpers.test.ts` refuses one written in SQL again.
