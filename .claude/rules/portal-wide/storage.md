# Files — Cloudflare R2, the database deciding who may

**FILES MOVE FROM SUPABASE STORAGE TO CLOUDFLARE R2 (2026-10-23 — the owner pasted an article on "Vercel + Supabase + Cloudflare R2" and said "open a worktree, i want do this"; asked what to move: "all data can move to r2 including crm"; asked who sets R2 up: wrangler, by Claude; asked about the public bucket: "现在开，DNS 搬 Cloudflare").** What was there: 10 buckets, 261 files, ~75 MB; 34 policies on storage.objects; 17 DEFINER functions reading storage.objects (did a file arrive, which files nobody holds). Uploads already went from the browser straight to Storage, so the article's 4.5 MB point never applied here.

**R2 keeps bytes and knows nobody — so WHO MAY stays in the database (the article's "check the role in a Vercel route" is NOT done: every gate asks a permission, and the database asks too).** Two tables, storage's own twins (mig `20261023150000_file_storage_r2`):
- `public.file_buckets` — storage.buckets' columns (public, file_size_limit, allowed_mime_types) + `backend` ('supabase' | 'r2') + `public_url` (a public bucket's address once in R2, `https://cdn.houzsventure.com/<bucket>`). Readable by every session and the stranger; nobody's to write but migrations.
- `public.file_objects` — storage.objects' columns (bucket_id, name, owner, owner_id text, metadata { size, mimetype }, created_at), carrying **every storage.objects policy word for word** (only `objects.name` reads `file_objects.name`; checked on production in a rolled-back run: 34 = 34, 0 differing; buckets 10 = 10). `file_objects_stamp` (BEFORE INSERT): for a session's row (anon / authenticated) the owner, owner_id and time are the database's, the bucket must be in R2, the name a path (no leading `/`, no empty / `.` / `..` part, no control character, ≤ 1024), the size and type within the bucket — in Storage's own words ("The object exceeded the maximum allowed size", "mime type x is not supported"); the metadata is kept as `{ size, mimetype }` (bare lower-case type). The service role's rows (the copy, the sweeps) are kept as given. Grants: authenticated SELECT / INSERT / DELETE, anon SELECT / INSERT (the guest link's job descriptions; the auto-reply pictures are public), nobody UPDATE.
- Registered as storage.objects never was: `audit_register` 'none' for both; `file_objects` is `READS_BY_BUCKET_POLICY` (lib/permission-table-reads.ts) and `NOT_A_DOMAIN_TABLE` in the writes test — one table-wide action list would close every other bucket.

**THE APP ASKS THE SAME WAY IT ALWAYS DID — `supabase.storage.from(bucket)`.** `withFileStorage` (lib/storage/server.ts) answers `.storage` on every server client — lib/supabase/server.ts (over the read-only client while viewing as somebody), admin.ts (the hourly sweeps), lib/guest/client.ts — and `withBrowserFileStorage` (lib/storage/browser.ts) on the browser's (lib/supabase/client.ts, lib/guest/upload.ts as the stranger). A bucket whose backend is 'supabase' is handed to Supabase Storage with the same arguments; one in R2:
- **upload** = the file's row under the CALLER's client (its bucket's INSERT policy and size / type rules decide), then the bytes. On the server: `r2Put` (If-None-Match `*`); a refused PUT takes its row back. From the browser: `startUpload` (Server Action, lib/storage/actions.ts) writes the row and answers a presigned PUT whose signature holds the type, the EXACT size and If-None-Match `*` — R2 itself refuses another file, a bigger one, or a second PUT over it — and the browser PUTs straight to R2 (never through a function). The guest page's `startUpload` acts as the stranger (`stranger: true` → `guestClient()`), never as whoever is signed in.
- **read** = select the row (the bucket's SELECT policy) → presigned GET (on R2's S3 address — R2 refuses presigning on a custom domain). `download` names it (RFC 5987 `filename*`); a type a browser could run (HTML, SVG, scripts, unknown) is only ever a download (`inlineSafe`, lib/storage/names.ts). The browser signs nothing: its link is `/files/<bucket>/<path>[?download=…]` (app/files/[bucket]/[...path]/route.ts, a read-only GET download) which looks the file up under the session and redirects to an hour's link — so a link kept on a page never runs out, and a video seeks (R2 answers Range with 206).
- **remove** = delete the rows the caller's DELETE policy lets go ("refused" = "nothing deleted", as Storage), then their files in R2. **copy** = read the source row, insert the copy's row, CopyObject inside R2.
- **public** = `file_buckets.public_url` + the name (getPublicUrl).
- `r2.ts` is the only module holding the R2 key (`'server-only'`, loaded only when a moved bucket is used). **No new service-role caller**: rows are written under the person's own session; the sweeps use the cron's existing client.

**THE TWO LEFTOVERS, CLEARED HOURLY (`sweepFileObjects`, member-queue cron):** a row whose file never arrived (the browser closed between the row and its PUT) and a file no row names (a row deleted while R2 would not delete just then) — each a day old, never younger, 200 a run, R2 buckets only.

**R2 ITSELF (created 2026-10-23 with wrangler, the owner's Cloudflare account — which also holds the Houzs ERP's `2990s-*` buckets: never touch those):** `houzs-venture-files` (every private bucket) and `houzs-venture-public` (every public one), both APAC; a key is `<bucket>/<name>`. CORS — private: GET / PUT / HEAD from erp.houzsventure.com, venture-portal-chi.vercel.app, `venture-portal-*.vercel.app` (previews) and localhost 3000 / 3001 / 3100 / 3150 / 3200 / 3300 / 3311 (ports cannot be wildcards — add one there if dev runs elsewhere), headers content-type / if-none-match / range; public: GET / HEAD from anywhere, and PUT from those same origins (the CRM's auto-reply pictures go up from the browser). The public bucket is served at `https://cdn.houzsventure.com` (R2's custom domain on the houzsventure.com zone, whose DNS moved from name.com to Cloudflare on 2026-10-23; TLS 1.2 and up): `crm-auto-reply/<name>` is `https://cdn.houzsventure.com/crm-auto-reply/<name>`. The app reads `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` (an R2 API token, Object Read & Write on those two buckets only), `R2_BUCKET`, `R2_PUBLIC_BUCKET`; until they are set a moved bucket's files answer "File storage (R2) is not configured on this server".

**MOVING A BUCKET (the runbook).** 1. `node --env-file=.env.local scripts/storage-to-r2.mjs --bucket <id>` (dry run), then `--apply`: bytes only, never over a file R2 holds, each read back (size + MD5 = Storage's ETag of a one-part upload). 2. The bucket's move migration (`*_file_storage_move_*`), ONE transaction: its rows copied from storage.objects (owner, time, metadata exactly Storage's), `backend = 'r2'`, and each function that read storage.objects for it pointed at `public.file_objects` — `pg_temp.repoint(sig, md5)`: production's own body with that one name swapped, refused when the body is not the one written against. 3. The script again, and the migration's `INSERT … SELECT` once more (a file sent the old way in the seconds around the flip — a page keeps the bucket list 5 s — gets its bytes and its row; both skip what is there). 4. Upload, open, download and delete one file as a real person. Storage's copies stay until the owner says to delete them.

**WHERE EACH BUCKET IS (keep this line current):** in R2 — all ten: `it-requests` (2026-10-23, the pilot: mig `20261023230000`), then the other nine (2026-10-23, mig `20261023233000`; the links saved in `crm_auto_replies.settings` rewritten from Storage's public address to the custom domain's). Still in Storage — none. Storage keeps its old copies until the owner says to delete them; before that, look for a link still naming Storage's address (`….supabase.co/storage/v1/object/public/…` — an auto-reply page left open over the move saves its old set back) and point it at the custom domain, or it breaks with them. The fixture of production's 17 bodies the moves swap (`tests/member-sql/storage-functions-production.json`, with their md5) is what `validate-file-storage-move.mjs` runs each move over.

**HOW BIG A FILE MAY BE (2026-10-23 — the owner, the morning after the move: "make the size more bigger for all, let me know the limit"; the night before: "make sure in future i can upload all big file, video and etc"; mig `20261024006700`):** a bucket's `file_size_limit` / `allowed_mime_types` in `file_buckets` are what `file_objects_stamp` asks of every file a session sends, and the app's own check says the same number first (keep the two together). **2 GB** — `hr-documents` (videos mp4 / mov / webm, PowerPoint and zip taken too; the preview drawer plays a video), `it-requests` and `marketing` (Marketing's Library, any type — mig `20261024007100`, `LIB_MAX_BYTES`). **100 MB** — `payment-attachments`, `hiring-files`, `attendance`, `member-forms`, `member-invoices` (documents and photos), and `crm-media` (WhatsApp's own ceiling, for a document — the CRM's code keeps each channel's limits, lib/member/crm-media.ts). **5 MB, unchanged** — `crm-showrooms`, `crm-auto-reply`: pictures WhatsApp sends, which takes none past 5 MB. Not R2's 5 GB: one upload is one request, and a bigger one lost near its end starts again from nothing (the link only has to START within 15 minutes; a file whose bytes never came is swept a day later). A size kept in a table is `bigint` (`hr_documents.file_size`, `it_request_files.size` …); `payment_attachments.file_size` and `member_request_attachments.size_bytes` are `integer` — fine to 2 GB, not past it. A file a page hands to a Server Action goes ahead of it (A FILE SENT AHEAD, below), so these limits hold there too.

**A FILE SENT AHEAD OF ITS SERVER ACTION (2026-10-23 — the same ask; mig `20261024006800`):** a Server Action's body stops at 4 MB (`next.config.ts`; a Vercel function takes 4.5 MB), so a page NEVER puts a file in one. It sends the file first to its sender's own folder of the private bucket **`uploads`** (100 MB, any type, R2 from the start; three policies on `file_objects`: a sign-in sends, reads and deletes only `<their own id>/…` — the stranger nothing) and puts a line naming it in the form in the file's place: `stageInto(form, field, files)` / `stageFiles(form)` (every File a finished form holds) / `stagedOnce()` (one copy for several actions — Invoice Financing's Auto-read, then its save) in `lib/storage/stage.ts`. The action reads it back under its own session — `formFile` / `formFiles` (`lib/storage/staged.ts`; a File from an older page still answers the same), then `file.bytes()` / `file.text()` where it had `arrayBuffer()` — and does with the bytes exactly what it did (looks at them, hashes them, files them where they always went, under the same policies), then `dropStaged` (or `dropStagedIn` for a refused form). What no action took, the hourly sweep clears a day later (`sweepFileObjects`, `stagedLeft`). Pages that do it: Payments (create, the voucher's Add attachments ×3 screens), Receipts, Invoice Financing (attach + Auto-read: a PDF up to 20 MB, a photo 5 MB — what the reader takes), Reconciliation (the statement, read, never kept), the waiting list's Upload form / "+" / a drawer's signed form, the Revenue app's invoices and signed forms (`member_request_attachments.size_bytes` and `member_waiting_add_form` / `member_waiting_attach_form` take 100 MB since this migration). A page's test mocks the trip: `vi.mock('@/lib/storage/stage', () => import('@/test/stage-in-place'))` keeps the File in the form. Not done: the CRM's showroom photo (Kaiyee's code, 4 MB, TODOS.md).

**A NEW BUCKET (Marketing's first, 2026-10-23):** a `file_buckets` row with backend 'r2' from the start, and its own INSERT / SELECT / DELETE policies ON public.file_objects (like a storage.objects policy, `bucket_id = '<id>'` first) in its own migration — never a Supabase Storage bucket. A page with no sign-in that shows a file (Marketing's `/t/<code>`) gives an anon client the code in a header (`global.headers: { 'x-link-code': code }`) and its SELECT policy asks a DEFINER function with `current_setting('request.headers', true)::json ->> 'x-link-code'` — nothing ever signs without the database saying yes.

**A PICTURE DRAWN ON A CANVAS IS FETCHED AFRESH (2026-10-24 — IT-0008's *Mark up screenshot* said "The image could not be opened" every time; the user: "this cant be use, fix it").** R2 answers a plain `<img>` (no `Origin`) with no `Access-Control-Allow-Origin` and no `Vary: Origin`; the browser keeps that copy and hands it to a later CORS load of the SAME link (`<img crossOrigin>`, a canvas export), which it then blocks — Supabase Storage always sent `*`, so this only began with the move. A page that reads a stored file's bytes in script (a canvas, `toBlob`) never sets `crossOrigin` on the shown link: it `fetch(link, { cache: 'no-store' })`s the bytes and draws its own `blob:` copy (`components/it-requests/ImageAnnotator`, the only such page today; its test names the case). Proved on production: the old load ERROR, the new one drew and exported IT-0008's picture.
