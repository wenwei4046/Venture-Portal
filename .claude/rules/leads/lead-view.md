# Lead View — Customer Service's inbox for the brands

Read this before changing anything under `/leads`, `src/lib/leads/` or the `lead_*` tables and functions, and again in every full scan of such a change (CLAUDE.md › Rules by tab). New decisions are added here, dated.

**WHAT IT IS (2026-10-16, the user):** one system where Customer Service answers the group's brands' enquiries — 2990s, 2990s mini, Carress, more later — from Messenger and Instagram (ads or organic; no WhatsApp channel), gets the customer's PHONE (Customer Service's KPI: 客服的 KPI 更多是在拿到電話號碼), and hands it to that brand's sales, who are NOT in the system (銷售團隊不會在這個系統中，會用自己的手機去聯繫客戶做預約). Desktop first. Three parts in the user's brief: manual replies; automation (an AI agent with a per-brand data center and "soul", and button flows); campaign blasting. The design is the Claude Design canvas "Lead View" (https://claude.ai/artifact/8cZ6TsUeWX6AYETkxQudiK), approved "1，2，3（中英）" — the UI writes Chinese and English side by side.

**PHASE 1 (2026-10-16, branch `lead-view`):** Inbox (three columns: conversations by brand / waiting · answered · handed / search; the chat; the customer card), Leads (the month's phones, hand-over and outcome), Insight (phone rate by brand, ad and who handed over; tests left out), Settings (brands with their Page / Instagram ids and hand-over mode, salespeople, and *Test* — a customer's message as if from Meta). Later phases, in order: flows (buttons), Data Center + AI as copilot (drafts), AI on its own (after hours first), Campaigns (opt-in only, Meta charges).
- **Where:** `/leads`, `/leads/list`, `/leads/insight`, `/leads/settings` under `(portal)`; PortalFrame draws Lead View's own shell on them (`isLeadViewPath`): the view sidebar with `lead-nav.ts`, HR's greeting bar saying *Lead View*. The view switcher's *Lead View* is not a mask — `setViewAs('lead')` clears the mask and opens `/leads`. An account whose cells open no Overview but hold Lead View lands on `/leads` from `/dashboard`.
- **Permission:** function `leads` (View · Create · Edit · Manage, reach all), key `leads` (scope none), Principal's role default, Ultimate / Full every cell (mig `20261016300000`). Tabs: a sixth view, *Lead View* (`lead.inbox`, `lead.leads`, `lead.insight`, `lead.settings`; Settings' Edit = `leads.manage`), so a template "Customer Service" can tick them — the tick tables' CHECKs and the functions that check a tick learned `lead` (mig `20261016300400`). The user: Customer Service has their own logins (one person today), title *Customer Service*; every reply shows who sent it.
- **Database:** `lead_brands`, `lead_sales`, `lead_contacts`, `lead_messages`, `lead_events` — RLS on, NO policy, no grants; every read and write is a `lead_*` DEFINER function asking `has_any_action` (mig `20261016300200`); the Inbox's create / edit writes also ask their page (`tab_write_guard`, mig `20261016300500`). The three brands are seeded. PGlite: `tests/member-sql/validate-leads.mjs`.
- **The phone:** `lead_find_phone` (SQL) and `findPhone` (`lib/leads/phone.ts`) find the first Malaysian mobile in a message — the same examples hold both; stored as digits (0123384721), shown 012-338 4721. A found phone is *detected* until Customer Service confirms it (or hands the lead over, which confirms it); the first phone stays.
- **Hand-over (the user: 可以):** a brand's salespeople are names and mobiles on Settings; the window suggests whoever had the fewest leads this week (rotate) or lets Customer Service pick, fills a WhatsApp message (editable), records `lead_handoff` and opens `wa.me` in a tab opened at the click. Appointment / came are kept by Customer Service on the card or Leads.
- **Meta is NOT connected (the user: 先把界面處理好再串接):** a reply is recorded (`delivery 'recorded'`), never sent; conversations arrive only through Settings › Test (`is_test`). Connecting later: the brands' Pages into Centralize Marketing Hub and the System User, their ids on Settings, the Messenger webhook routing a brand's Page to a lead ingest function (the CRM's Pages keep going to the CRM). Messenger permissions are the app's (no new review per Page); Instagram messaging needs its own App Review.
- **Not applied:** the six migrations wait for the user's yes; until then the pages say *Lead View's database is not set up yet*.

**APPLIED TO PRODUCTION (2026-10-16, the user: "Yes, apply the six"):** migs `20261016300000`–`300500`. Two CHECKs moved names: `permission_functions.section` takes Daily / People / Departments / Reports / Admin (Lead View is *Daily*), `audit_tables.area` takes the portal's areas (Lead View's tables are *Member services*, as the CRM's). The tab seed went in insert-only — production's registry was exactly `20261016140000`'s, so the end state is the file's row for row (md5-checked). Demo data (six conversations marked TEST, salespeople named "(示範)") was put in at the user's word ("我主要是要看功能") — clear it, listed first, before going live. While every conversation is a test, Leads and Insight show them and say so.

**PHASE 2 — FLOWS (2026-10-16, the user's brief 2.2; built after "先做其他的", not live):** `/leads/flows` (tab `lead.flows`: View, Edit = `leads.manage`). A flow (`lead_flows`, mig `20261016310000`) is a brand's or every brand's steps — question (text + up to 13 buttons, 20 characters each), message (then straight on), phone (waits for a mobile number), handoff (ends; the conversation waits for Customer Service) — started by the conversation's FIRST message: an ad whose name holds the trigger, else a keyword in the message, else "any first message"; a brand's before every brand's. It runs in the database, in a DEFERRED constraint trigger on `lead_messages` (`lead_flow_on_message` → `lead_flow_send`), so no message writer changes (Test now, Meta's ingest later) and it runs after the writer has set the conversation's columns. A typed answer that is no button stops it, and so does Customer Service's reply. `lib/leads/flow.ts` is the twin (`flowProblem`, `sendFrom`, `answerStep`) — the editor checks before saving and its "Try it" phone runs the steps without sending anything. Lead View · Manage now stands behind Settings' and Flows' Edit, so the brand, salesperson and flow writes ask their page (mig `20261016310100`).

**AUTOMATIONS REPLACE THE TREE (2026-10-16 — the user: "我更希望的是客服可以创建属于自己的 workplace，可以分为 general、广告 etc；这个树状图不容易理解", showing Meta's "create automation"; the canvas's "自動化" row, approved "可以"; mig `20261016320000`, APPLIED at the user's yes):** `/leads/flows` is *Automations*: Customer Service's own categories (`lead_auto_categories` — add, rename, delete; an automation keeps living with no category), each automation a card with its switch, and "+ New automation" opens the templates by goal as Meta's — Greet (Welcome, Away), Share information (FAQ, Location, Opening hours, Custom keywords — Location and Hours are keyword presets), Ads (Ad Q&A), Manage (Unanswered reminder — *coming soon*), and *Start from scratch* (the step tree, kept). A template is a short form (`lead_flows.template` / `config`); `lib/leads/automation.ts` `compile` turns it into the steps the runner already runs. The runner learned: trigger `away` (outside `config.hours`, Asia/Kuala_Lumpur, `lead_is_away`; at most once in 12 hours a conversation); a keyword (comma-separated list) or away automation also answers a LATER message while no flow is waiting and Customer Service has not replied in 12 hours; first message: ad › keyword › away › any-first; a question's `saveAs` writes the tapped answer into the card (interest / budget / showroom / preferredTime). Demo data: three "(demo)" automations (the ad one on, FAQ and After-hours off); the seeded category 廣告 was renamed **Ads** on production.

**ENGLISH FIRST, SIMPLIFIED CHINESE AS THE HELPER (2026-10-16, the user: "简体+英文；英文大点，中文辅助翻译"):** every Lead View screen writes English, with Simplified Chinese beside it smaller (`Bi` in `_components/bits.tsx`, `.zh` / `.zhBlock`) — no Traditional Chinese in the interface. The hand-over WhatsApp text is English + Simplified too.

**AI AGENT, THE BASE (2026-10-16 — the user's brief 2.1, then "这个完成后做AI Agent，把基础做好，细节再调" / "是的"; migs `20261016330000` / `330100`, APPLIED at the user's yes — the registry seed insert-only, production's being `310100`'s exactly; md5 equal to the file after):** the agent is a COPILOT — it writes drafts; a person sends, edits or dismisses each one, and nothing it writes reaches a customer by itself. Answering on its own (after hours first), photos and uploaded files are later.
- **Data Center** (`/leads/knowledge`, tab `lead.knowledge`): `lead_knowledge` — short text cards (promo · product · FAQ · showroom · policy · note) for one brand or every brand, with optional dates and an on switch. A brand's agent reads its own cards and every brand's that are on and in date (`lead_knowledge_today`, office days; twin `inDate`). The prompt tells it to quote prices, promos, stock, addresses, hours and policies ONLY from the cards, else say a colleague will confirm and flag a hand-over.
- **The soul** (`/leads/ai`, tab `lead.ai`): `lead_personas`, one per brand — name, personality, tone (warm · professional · playful · concise), goal (default: get the mobile number for a showroom visit — the KPI), always / never, example replies (voice, not facts), mode off · copilot. A brand with no row is off. The page shows each brand's last 30 days of drafts (sent as is / edited / dismissed, the adoption rate) and a **Try it** chat that runs the soul ON THE FORM (saved or not) with today's cards; nothing is kept.
- **The Inbox's AI draft:** on a copilot brand's conversation, "✦ AI draft" → `draftLeadReply`: `lead_ai_context` (the soul, today's cards, the card, the last 30 messages; refused while the brand's agent is off) → the model → `lead_ai_log_draft` (`lead_ai_drafts`; a newer draft passes over an unused one). Use puts it in the reply box; the reply's send records `sent` (as written, spaces aside — `outcomeOf`) or `edited`; Dismiss records `dismissed`. The draft shows the cards it used and the agent's hand-over flag and note.
- **The model** (`lib/leads/ai-model.ts`, server only): Claude Opus 5.5 (`claude-opus-5-5`), adaptive thinking at low effort, structured JSON output (`DRAFT_SCHEMA`, checked again by `readDraft` — only the card ids it was given), the system prompt (soul + cards) cached, and **server-side refusal fallbacks on** (`fallbacks: 'default'`, beta `server-side-fallback-2026-07-01`). The key is `ANTHROPIC_API_KEY` in env (Vercel, `.env.local`) — the user adds it themself; without it the AI Agent page and the draft say "not connected". The prompt and the reading of the answer are pure (`lib/leads/ai.ts`, `ai.test.ts`).
- **Permissions:** Data Center and AI Agent read with Lead View · View and edit with Manage (their writes ask their page, `tab_write_guard`); the Inbox's draft functions ask Lead View · Create on `/leads`. The tables have RLS on, no policy, no grants, as the rest. PGlite: `validate-leads.mjs` (AI section).
